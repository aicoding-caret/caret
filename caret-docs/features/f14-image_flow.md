# Antigravity Image Processing & Generation System (Full Guide)

이 문서는 Antigravity 에이전트 시스템에서 이미지를 업로드, 분석, 수정 및 생성하는 모든 기술적 메커니즘과 구현 원리를 상세히 기록한 가이드입니다.

---

## 1. 이미지 업로드 및 최적화 메커니즘 (Optimization)

사용자가 이미지를 업로드하거나 붙여넣는 순간부터 시스템은 효율적인 처리를 위해 작동합니다.

### A. 리사이즈 및 포맷 변환 타이밍
단순히 원본을 전달하는 것이 아니라, 성능과 비용(토큰) 조절을 위해 두 단계의 최적화가 발생합니다.

*   **프론트엔드 (업로드 시점):**
    *   **동작:** 사용자가 파일을 선택하거나 클립보드에서 붙여넣는(Ctrl+V) 즉시 자바스크립트가 개입하여 브라우저의 Canvas API를 통해 해상도를 조정합니다.
    *   **기준:** 대개 긴 축 기준 2048px 이하로 리사이즈하며, 용량을 줄이기 위해 JPEG/WebP로 압축합니다.
    *   **이유:** 업로드 속도(대역폭 절약)를 높여 사용자의 대기 시간을 줄이기 위함입니다.
*   **서버/게이트웨이 (API 호출 직전):**
    *   **동작:** 프론트엔드 최적화를 거치지 않고 들어온 데이터(외부 API 등)를 검증하고, AI 모델이 요구하는 최적 해상도로 다시 한번 조정합니다.
    *   **이유:** 모델의 입력 토큰 제한을 초과하지 않고, 추론 비용을 최적화하기 위함입니다.

## 2. LLM과 이미지 엔진의 협업 구조 (Cognition & Creation)

이미지 생성 시 **LLM(두뇌)**과 **이미지 엔진(화가)**은 '지시서'와 '밑그림'의 관계를 맺습니다.

### A. 감독(LLM)의 역할: 분석 및 지시서 작성
LLM이 이미지를 함께 받아서 분석해야만 정교한 제어가 가능합니다.
*   **의도 구체화:** 사용자 요청이 모호하더라도(예: "좀 더 힙하게") 이미지를 분석하여 "네온사인이 빛나는 사이버펑크 스타일로 변환"과 같은 구체적인 **기술 지시서(Prompt)**를 생성합니다.
*   **맥락 파악:** "저기 멀리 보이는 산을 지워줘"와 같은 지시에서 '멀리 보이는 산'의 시각적 특징을 정의합니다.

### B. 최종 API 호출 시 전달 데이터: 왜 둘 다 보내는가?
이미지 생성 API를 최종 호출할 때 **LLM이 분석한 프롬프트**와 **원본 이미지**를 **반드시 동시에** 전달해야 합니다.

1.  **원본 이미지 (밑그림/뼈대):** 이미지 엔진에게 피사체의 위치, 형태, 구도, 빛의 방향 등의 '구조적 유전 정보'를 제공합니다.
2.  **분석된 프롬프트 (수정 지시서):** 엔진에게 "무엇을 어떻게 바꿀 것인가"에 대한 명령을 전달합니다.

*   **주의:** 텍스트(프롬프트)만 보낼 경우, 엔진은 원본이 무엇인지 모른 채 처음부터 다시 그리는 **'재생성(Remake)'**을 하게 되어 원본의 정체성이 사라집니다. 둘 다 보내야만 원본의 뼈대를 지키며 수정하는 **'정밀 편집(Edit)'**이 가능해집니다.

## 3. 이미지 기반 생성(Image-to-Image) 표준 워크플로우

사용자가 이미지를 업로드하고 "기반으로 생성해줘"라고 요청했을 때의 실제 매커니즘입니다.

1.  **LLM에 이미지 및 텍스트 전달:** 사용자의 의도와 분석 대상 이미지가 LLM의 컨텍스트로 한꺼번에 전달됩니다.
2.  **분석 (Reasoning):** LLM이 이미지를 시각적으로 파악하여 특징을 추출합니다.
3.  **이미지 툴 호출 (Tool Calling):** 분석 결과를 바탕으로 `generate_image` 툴을 호출합니다. 이때 **[원본 이미지]**와 **[LLM이 분석/보강한 상세 프롬프트]**가 함께 이미지 API로 전송됩니다.
4.  **이미지 생성 (Generation):** 이미지 엔진은 원본의 '구조'와 프롬프트의 '내용'을 결합하여 새로운 이미지를 렌더링합니다. (이미지 유전 정보를 유지하면서 지시사항 반영)
5.  **프론트 전달:** 생성된 결과물을 Base64 형태로 인코딩하여 사용자에게 즉각 반환합니다.

---

## 4. 시스템 아키텍처 및 라우터 설계 (Router Design)

### A. 라우터 분리 원칙
*   **`/v1/chat/completions` (Chat Router):** 대화 맥락, 히스토리, 텍스트 추론 담당.
*   **`/v1/generate/image` (Image Router):** 이미지 생성 파라미터(비율, 사이즈), 대용량 바이너리(Base64) 처리 담당.
*   **분리 이유:** 
    *   입출력 규격 및 과금 체계(토큰 vs 장당)의 차이.
    *   이미지 생성의 긴 타임아웃 관리 및 인프라 확장성 확보.

### B. 통합 에이전트 인터페이스
사용자에게는 하나의 채팅 인터페이스를 제공하되, 뒤에서는 **Tool Calling**을 통해 Chat API가 필요 시 내부적으로 Image API 로직을 트리거하여 협업합니다.

---

## 5. 핵심 기술 요약

*   **Multimodal Integration:** 텍스트와 이미지를 단일 입력으로 처리하여 깊이 있는 시각적 이해 실현.
*   **Dual-Layer Optimization:** 전송 속도(프론트)와 토큰 비용(서버)을 고려한 전략적 리사이즈.
*   **Reasoning-Based Generation:** 이미지 엔진 호출 전 LLM의 분석 단계를 거쳐 생성 결과의 정확도와 품질을 보장함.
*   **Blueprint Strategy:** 원본 이미지(뼈대)와 지시서(내용)를 함께 전송함으로써 단순 생성이 아닌 의도된 변형(Image-to-Image)을 가능케 함.
